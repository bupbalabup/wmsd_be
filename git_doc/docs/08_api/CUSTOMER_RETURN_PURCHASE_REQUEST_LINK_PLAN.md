# Customer return links to purchase requests and goods issues

Design review of 2026-11-26. The subsequent implementation supports several issues from one purchase request and warehouse. The [current return contract](RETURN_WORKFLOWS_NATIVE.md#purchase-request-and-goods-issue-links) supersedes the one-issue assumption in this original proposal.

## 1. Outcome

From a customer return, staff can open the original **Yêu cầu mua hàng của khách**, see its related **Phiếu xuất bán**, and identify exactly which issue supplied the returned goods. During creation, staff can start with a request or with a goods issue. One purchase request can have several issues. Each return continues to use one source document and can include several lines or split parts from it.

## 3. Implementation order

1. **FR-01 · Must · Resolve the relationship on the server.** Resolve the request from the selected issue source. Follow `GI.header.salesOrderId` and verify the issue line’s `salesOrderItemId` for direct issues. Follow the existing issue line → outbound-delivery line → warehouse issue request → SalesOrder chain for legacy issues. Reuse the chain checks in `native.shared.js`, with a read-only path for detail and picker queries and the existing transaction and source lock for writes. Expose a read-only return detail projection with the source issue summary and optional purchase-request summary, including stable ID and document number. Resolve existing returns from their saved source lines. Leave their free-text reference readable as a manual reference. This design uses existing persisted identities and needs no migration or backfill.
2. **FR-02 · Must · Add request-first source selection.** In `/returns/create`, select the handling warehouse, optionally choose a customer purchase request, then show its goods issues and source lines for that warehouse. Provide a scoped, paged request lookup that searches by document number and includes fulfilled requests. Reuse the existing GI list filter where the caller has `goods_issue:read`, or extend the return-source lookup to expose issue summaries to eligible return creators under the current return permissions. Scope by the resolved request ID and warehouse before pagination. Show issue number, status and remaining returnable quantity. The create flow selects only eligible issue lines and their recorded lots. Changing warehouse, request or issue clears incompatible staged rows. Continue to offer direct issue and verified historical lookup.
3. **FR-03 · Must · Validate and save against actual issue lines.** Continue submitting `salesIssueLineId` or `historicalExternalLineId`, with `lotId` where applicable. If the request-first form sends an optional selected `salesOrderId`, validate it as a DocumentIdentity and compare it with the request resolved from every selected issue line. Treat it as a consistency check. Persist the existing source references. Within the current idempotent transaction, enforce warehouse and actor scope, one source document, actual customer receipts where required, remaining claims, and lot limits. A draft issue, in-transit issue with zero confirmed receipt, fully claimed issue or issue belonging to another request cannot supply the return. Eligible quantities from separate issues on the same request can each produce their own return.
4. **FR-04 · Must · Add navigation to the return detail.** Show the original request and the exact source issue in the detail or related-documents panel. Link to `/orders/:id` and `/goods-issues/:id` when the user can open them. Show the request’s authorized related issues with the return’s source issue marked. Use a scoped list query, with status and warehouse shown for each visible issue. For standalone and historical sources, display the relevant source or external reference with its existing access rules. Keep the issue selected when a user starts from a goods-issue link and validates that source on load.
5. **FR-05 · Should · Add a reverse entry point.** Add “Tạo đề nghị khách trả hàng” to eligible purchase-request and goods-issue detail screens when the user has return creation access. Preselect the originating request or issue. Recheck availability on entering the form and on save.
6. **Release and documentation.** Ship the additive backend read contract before or with the frontend. Run the verification cases below on an isolated MongoDB replica set, then smoke-test Sales and Warehouse in the browser. Update the return, goods-issue and sales-order API contracts, frontend context, and changelog. Model documentation is needed only if a persisted relationship is later approved.

## 4. Decisions and risks

- **DEC-01 · Recommended:** Derive the link from the source issue for stage one. This also works for earlier returns with intact source chains. A persisted request ID could make future reverse lookups cheaper, but would duplicate the relationship and require a schema and consistency decision.
- **DEC-02 · Working assumption:** Keep one source goods issue per return. Allowing a return to span several issues changes the current validation, claim grouping, and operational review. Confirm separately if that is needed.
- **DEC-03 · Existing behavior:** Completion defaults an unset delivered quantity to the open quantity, which then qualifies as a recorded customer receipt. Confirm whether Warehouse must explicitly enter the quantity before completion if this default is unacceptable for returns. The link work uses the existing receipt policy.
- **RISK-01 · High likelihood, high impact:** Using request progress for eligibility can let the UI offer in-transit units. Mitigate with FR-03 and the handover test below.
- **RISK-02 · Medium likelihood, high impact:** Order-wide summaries can reveal documents from another warehouse. Mitigate with server-side row scope and negative tests for custom roles, Sales ownership, and cross-warehouse records.
